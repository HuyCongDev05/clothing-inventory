Đặc tả quan hệ Use Case trong Báo cáo:
• UC-01 (Đăng nhập): Bắt buộc «include» việc xác thực mật khẩu băm BCrypt qua AuthenticationManager và phát hành cặp Dual-Token (Access Token lưu tại bộ nhớ Client, Refresh Token lưu trong HttpOnly Cookie & Redis).
• UC-03 (Tự động làm mới phiên ngầm): Quan hệ «extend» mở rộng từ UC-02 (Truy cập API bảo vệ), được kích hoạt tự động khi nhận mã lỗi HTTP 401 Unauthorized mà không làm gián đoạn trải nghiệm người dùng.
• UC-04 (Cưỡng chế đăng xuất): Được mở rộng kích hoạt khi Refresh Token trong Cookie hoặc Redis hết hạn (TTL 7 ngày kết thúc) hoặc tài khoản bị vô hiệu hóa.

Hình 3.4.1.C: Sơ đồ Tuần tự Chi tiết Luồng Làm mới Phiên ngầm & Hàng đợi chống Race Condition (OMG UML 2.5)

Hiện thực hóa chính xác mã nguồn apiFetch.ts, JwtAuthFilter.java, AuthController và Redis Cache Server

OMG UML 2.5 Sequence Diagram
:User «boundary» :apiFetch «control» :JwtAuthFilter «control» :AuthController «entity/storage» :JwtUtil / :Redis 1: fetchProducts() 2: GET /api/v1/products [Bearer expiredToken] 3: verifyToken(expiredToken) 4: throw JwtValidationException("Token expired") 5: return 401 Unauthorized (UNAUTHORIZED_ACCESS) opt [isRefreshing == true: Concurrent requests queue] 6: subscribeTokenRefresh(callback) alt [Refresh Token valid in HttpOnly Cookie & Redis] 7: POST /api/v1/auth/refresh-token [Cookie: refresh_token] 8: verifyToken(refreshToken) 9: return JwtClaims(uuid, type="refresh_token") 10: get("refresh_token:" + uuid) 11: return matched (Token verified in Redis) 12: generateAccessToken(uuid, authorities) 13: return newAccessToken (TTL 15m) 14: return 200 OK { data: { accessToken: newAccessToken } } 15: localStorage.setItem("accessToken", newAccessToken); onRefreshed() 16: [RETRY] GET /api/v1/products [Bearer newAccessToken] 17: SecurityContextHolder.setAuthentication(auth) 18: return 200 OK { content: [products] } 19: renderView(products) [Seamless UX] [else: Refresh Token expired or revoked in Redis] 20: return 401 Unauthorized (UNAUTHORIZED_REFRESH_TOKEN) 21: clearSessionAndRedirect(/login) 22: redirectToLoginView()
Giải thích các điểm kỹ thuật cốt lõi theo chuẩn UML 2.5:
• Khối opt [isRefreshing == true]: Áp dụng cơ chế đăng ký callback (subscriber queue) để gom các request đồng thời trong lúc tiến trình làm mới token đang diễn ra, ngăn chặn triệt để hiện tượng tranh chấp (Race Condition).
• Khối alt: Phân nhánh rõ ràng giữa kịch bản lý tưởng (Refresh Token hợp lệ trong Cookie & Redis ➔ cấp token mới và tự động gửi lại request ban đầu với trải nghiệm mượt mà Seamless UX) và kịch bản bất thường (Refresh Token hết hạn ➔ xóa sạch phiên và điều hướng về trang đăng nhập).
